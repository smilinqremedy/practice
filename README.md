## Project Overview

Learn2Earn provides fellows with equipment such as laptops, keyboards, and headsets to support their learning journey. This system ensures:
- Full traceability of available and total inventory.
- Strict validation on loans and returns preventing stock discrepancies.
- Case-insensitive searching and category filtering.
- Automatic aggregation of fleet health and demand metrics.
- State preservation with non-mutating validation failures.

## How to Run

No external dependencies are required. Runs with standard **Python 3.8+**.

### 1. Interactive Menu Mode
Run the interactive CLI application:
```bash
python3 app.py
```

### 2. Automated Demonstration Runner
Execute the 7 required steps and invalid-input tests in order:
```bash
python3 demo.py
# or
python3 app.py --demo
```

### 3. Run Unit Test Suite
Execute the comprehensive automated test suite (16 test cases):
```bash
python3 test_learn2earn.py
```

## A3. Project Design Explanation

### 1. Key Functions
The system uses modular, single-responsibility functions:

1. **`borrow_resource(resources, fellows, borrow_records, fellow_id, resource_id, quantity)`**:
   Validates fellow registration, resource presence, positive integer quantity, and available inventory. Only after all preconditions pass does it deduct inventory stock and record the active loan in `borrow_records`. If any check fails, state is completely unmutated.
2. **`return_resource(resources, fellows, borrow_records, fellow_id, resource_id, quantity)`**:
   Verifies that the fellow has an active loan for the specified resource and that the return quantity is $\le$ the currently borrowed quantity. Decrements or removes the loan from `borrow_records` and restores the resource's `available` stock.
3. **`generate_reports(resources, borrow_records)`**:
   Calculates global inventory metrics (overall total units, available units, and borrowed units). Flags items with $< 3$ units available as low stock. Calculates borrowed counts per item and identifies the highest borrowed item(s), correctly reporting all tied leaders if multiple items share the maximum.
4. **`add_resource(resources, resource_id, name, category, total)`**:
   Validates inputs, ensures total units $> 0$, and enforces ID uniqueness across the inventory. Sets initial `available` equal to `total`.
5. **`search_resources_by_name(resources, query)`** & **`filter_resources_by_category(resources, category)`**:
   Performs case-insensitive substring searching and category filtering over the resource collection.
6. **`save_to_json(...)`** & **`load_from_json(...)`**:
   Implements bonus JSON serialization and deserialization, safely writing and recovering system state to and from disk.

### 2. Data Representation

- **Inventory (`resources`)**:
  Represented as a `list` of `dict` objects:
  ```python
  resources = [
      {"id": "R001", "name": "Laptop", "category": "Electronics", "total": 10, "available": 10},
      {"id": "R002", "name": "Keyboard", "category": "Accessories", "total": 5, "available": 5},
      {"id": "R003", "name": "Headset", "category": "Accessories", "total": 3, "available": 3}
  ]
  ```
  Each dictionary encapsulates an item's unique identifier, name, category, immutable overall pool (`total`), and mutable current in-stock pool (`available`).

- **Fellow Loans (`borrow_records`) & Fellows Registry (`fellows`)**:
  - `fellows` is a dictionary mapping fellow IDs to fellow names:
    ```python
    fellows = {"F001": "Ada", "F002": "John", "F003": "Grace"}
    ```
  - `borrow_records` is a list of active loan dictionaries:
    ```python
    borrow_records = [
        {"fellow_id": "F001", "resource_id": "R001", "quantity": 1},
        {"fellow_id": "F002", "resource_id": "R002", "quantity": 3}
    ]
    ```
    This representation makes lookups and updates straightforward: returns decrement active loans, and completed returns remove the loan record when the borrowed quantity reaches zero.

### 3. Design Limitation
**In-Memory Concurrency & Audit Traceability**:
The current design stores active state in-memory (with optional flat JSON serialization). Because there are no database transactions or locking mechanisms:
1. It does not support concurrent access (multiple simultaneous loan officers would cause race conditions).
2. `borrow_records` maintains current active loans rather than an immutable, timestamped audit log of all historical events (e.g., date borrowed, due dates, return timestamps, condition notes). In a production lending system, an append-only transaction ledger with timestamps and a relational database (such as PostgreSQL or SQLite) would be preferred.

## Optional Bonus: JSON Persistence

The system provides persistent storage to JSON using `save_to_json` and `load_from_json`.
Sample saved JSON (`learn2earn_data.json`):
```json

    {"id": "R001", "name": "Laptop", "category": "Electronics", "total": 10, "available": 9},
    {"id": "R002", "name": "Keyboard", "category": "Accessories", "total": 5, "available": 2},
    {"id": "R003", "name": "Headset", "category": "Accessories", "total": 3, "available": 3}
  ],
  "fellows": {
    "F001": "Ada",
    "F002": "John",
    "F003": "Grace"
  },
  "borrow_records": [
    {"fellow_id": "F001", "resource_id": "R001", "quantity": 1},
    {"fellow_id": "F002", "resource_id": "R002", "quantity": 3}

```
